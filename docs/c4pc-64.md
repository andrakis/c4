# The 64-bit C4IX on a PC

C4IX's `int` is the machine's word. On libjs and c4pc it is 32 bits; on
native c4m (c4m.c) it is 64, and `make c4ix.c4r` builds that C4IX with
lc64. Until now the PC ran only the 32-bit one: c4pc's engine is
libjs's, and libjs's word is 32 bits (c4pc64.elf is that 32-bit machine
compiled for an x86-64 host). This is the 64-bit machine beside it, and
the 64-bit system on it: a PC now boots either.

## One source, two words

c4pc.h:

```
#ifdef C4PC_W64
typedef int64_t word; typedef uint64_t uword;
#define WB 8     /* bytes */   #define WSH 3   #define WBITS 64
#else
typedef int32_t word; typedef uint32_t uword;
#define WB 4                   #define WSH 2   #define WBITS 32
#endif
```

Everything that is a guest's word is a `word`: the registers (pc, sp, bp,
a, mode), the trap handler and cycle handler, the signal handlers, the
CPU-local window, the arena seen as words (`machine.w`). Everything that
moves by a word moves by WB: the stack, pc, LEA/ENT/ADJ's operands
(scaled by WSH), a trap's frame (15 words below sp, the handler at its
ENT plus two words), a syscall's arguments (sp, sp + WB, ...), PRTF's,
the trampoline and argv. Shifts take their count mod WBITS, and LSR is
WBITS wide; C4CY gives the whole cycle count on 64 bits (c4m's `a =
cycle`), its low 32 on 32. Arithmetic still wraps (`-fwrapv`, uword
casts), DIV and MOD by 0 still give 0 and INT_MIN / -1 INT_MIN, as libjs
has them (native c4m divides as the host does, which faults), so that a
64-bit program meets the same answers as a 32-bit one.

On the 32-bit build every one of those is the expression it was (WB 4,
WSH 2, `word` int32): the loop is the same code, and `make test-c4pc`
passes as before, every session byte for byte and cycle for cycle
libjs's, with the MMU and without, the accelerators, 4 CPUs, the
programs.

The arena stays under 4 GB (2 GB at most, a power of two) at either size,
so an address known to be inside it is a u32; a 64-bit address past 4 GB
is past the arena, and is given to a device as 0xFFFFFFFF (engine.c A32),
never as its low bits. A count past 2^31 is 2^31 - 1 (N32): MALC of 4 GB
is no memory, not 0 bytes.

### Images

A .c4r's byte 4 is its word size; the loader (engine.c machine_boot, as
load-c4r.c and src/c4ix/loader.c) refuses another. On 64 bits the header's
lengths, the code, the patches (type, address, value), the constructors
and destructors are 8-byte words, and a symbol record is id, type, class,
attrs (words), the name's length (a byte), the name, the value (a word):
`4 * WB + 1 + n + WB` bytes, 17 + n + 4 on 32 bits. Data follows the code
at the next word.

### The memory map

The same bytes at either size. The null guard is 0x0-0xF (four words, or
two), TLEV's word is at 0x10 and CPUH's at 0x18, the opcode names at
0x200, the program's code from 0x1000.

The device registers stay where they are, 4 bytes apart and 32 bits
wide (dev.c, gui.c, snd.c, the block devices' window): a word load at
0x1F4 is IMG_DATA's value, sign-extended; a word store keeps its low 32
bits. C4IX addresses every register by its own address (c4ix.h, gui.h,
snd.h), never as an array of words, so its sources are the same at both
sizes. No register's value needs more than 32 bits.

The CPU-local window is 64 words from 0x800: 0x800-0x8FF on 32 bits,
0x800-0x9FF on 64 (c4ix.h CPU_WINDOW, CPU_SLOT0 and CPU_SLOTS index it by
word). Nothing else is between 0x900 and 0x1000.

### What the devices read in memory

What a device reads or writes as bytes is the same at either size: files
(OPEN, READ, the drives), the console, the keyboard, swap pages, sectors
(the block devices), CDs, a PCM sample's bytes. What it reads as the
program's words is words of WB bytes, each value in the low 32 bits, as
libjs/guest/gui.c and snd.c write them at either size:

- the display's rings (gui.c rdw/wrw by word index; the ring's halves
  aligned to a word), its frames' payloads, an image's pixels, BLIT8's
  palette (256 words), the framebuffer's pixels (a pixel a word; pitch 0
  means w * WB). Text is four characters a word, the lowest byte first,
  in the low 32 bits (gui_chars);
- the sound card's PCM_START block: five words;
- C4IX's accelerators (accel.c): CX_INFLATE's state, 14 words
  (archive.c cx_st), and the Huffman tables, words; CX_CRC32's result is
  the CRC zero-extended on 64 bits, as archive.c's `& 0xFFFFFFFF` leaves
  it. The games' accelerators are the 32-bit machine's only.

### Floats

FPU and FLT take a float as its 32 bits in a word, and give one back
zero-extended (c4m_float.c's `(int)` of an unsigned 32-bit value). A
double is 8 bytes at an address, two words on 32 bits and one on 64
(fpu.c dload, dstore; fpu_double_plain now takes byte addresses for both).
The integer conversions are the word's: sub-ops 7 and 23 convert a 64-bit
integer (to a float rounded once, from the integer, not through double),
8 and 24 give softfp.c's `__c4f_to_ll` / `__c4d_to_ll` (the most negative
for what does not fit), and FLT's ITOF and FTOI likewise.

### PRTF

On native c4m PRTF is the host's printf given the words, so a 64-bit
program's `%d` prints the low 32 bits and `%ld` the word. fmt.c does the
same on 64 bits: `%d %i %u %x %X %o %c` take the low 32 bits, and with
`l`, `ll`, `j`, `z`, `t` or `q` the whole word; `%p` and `%s` the whole
word. `%f %e %g` stay libjs's (a binary32's bits), where c4m's printf
reads a register the word was never in.

### INFO

The 64-bit machine announces what the 32-bit one does:
C4I_C4MJS and the devices, so the 64-bit C4IX takes libjs's way (its
drives, the boot report's IMG_* and BOOT_* registers, the PIT, the
display). `c4pc-host64w --c4m` announces native c4m's instead (C4M, HRT,
SIG, FLT, PROT, FPU, TRAPH): no devices, files by OPEN, as on c4m.c. That
is how the 64-bit machine is held against native c4m on c4m's own tests.

### The MMU at 64 bits

docs/c4ix-mmu.md's MMU, libjs/mmu.js's (c4pc's mmu.c), has two levels of
page tables, each a 4 KB page of entries: on the 32-bit word 1,024 of 4
bytes, the i386's shape, 10 + 10 + 12 bits of address. On the 64-bit word
an entry is a word too, so a table holds 512 of 8 bytes and a directory
entry covers 2 MB: 9 + 9 + 12 bits, 1 GB in all. That is enough: C4IX's
user addresses are 256 MB from 0x10000000 (MMU_UWIN_BASE), and c4pc's
translation arrays cache 512 MB of pages (LIMIT). An address past 1 GB
maps nothing (mmu.c VA_OK), where a 32-bit index would wrap. The bits in
an entry are the same (P W U X A D, PTE_PIN, PTE_SWAP; the frame above
bit 12).

- C4IX's src/c4ix/mmu.c indexes its tables through MMU_PTES (MMU_PAGE /
  sizeof(int)) and MMU_DSHIFT (22 - (sizeof(int) >> 3)), which c4lc folds
  to constants: the 32-bit mmu.c4o is byte for byte what it was. One real
  bug went with them: mmu_vbits, the window's page bitmap, was allocated
  WINPAGES / 8 bytes and indexed by word, 8 KB past its end on 64 bits.
- c4pc's mmu.c had engine.c's conversion: the user loop's registers, its
  stack and code windows and the slow paths are words; the stack window
  wants a word either side of sp, and its look-ahead counts words; the
  code window's last word is left out of it, and its look-ahead counts two
  words an instruction; a block opcode's part-way state, the fault
  registers and the FPU's operands are words; a page number stays wide,
  so that an address past 2^44 cannot alias a low page.
- The user window (engine.c kpa, kld32, kblock; dev.c dma) was word-clean
  already, and is on now.

### Not on 64 bits yet

- **The games' accelerators** (games/NAME.c) and their kit's held writes
  and scratch: the games are on the 32-bit system.
- **An i386 build of the 64-bit machine**: c4pcw64.elf is x86-64 only
  (the interpreter's 64-bit word wants 64-bit registers; a PC without
  long mode boots the 32-bit system).

## The 64-bit system's disk

src/c4pc/disk64.sh is the C4IX part of src/c4bb/tests/build-images.sh
with lc64 (c4sc-host: c4lc compiled for the host, whose images are
64-bit) and the 64-bit c4rlink:

- the kernel: make's c4ix.c4r (`-D C4IX_LFS`: 64-bit file positions,
  free on this word, docs/c4ix-lfs.md);
- libc4ix and libarc static (for vfsload and splash), and the shared
  libraries libc4ix.c4s (with window.c and cpustat.c), libarc.c4s,
  libgui.c4s (gui.c and snd.c) and libc.c4s, `-fpic`, as the 32-bit disk
  has them (libarc `-mfuse`, as src/c4ix/lib/BUILD.B4K builds it);
- every program of build-images.sh's C4IX_USER and C4IX_ARC_USER, linked
  against the shared libraries (splash and vfsload static);
- the desktop: its modules and the window kit's, and libc's fp.c;
- the toolchain cc and b4ke run: c4sc.c4r and cpp.c4r (make's; b4ke's
  src/c4cc/BUILD.B4K runs cpp), and c4cc.c4r, c4rdump.c4r and c4rlink.c4r
  built by the native c4cc as build-images.sh builds them; c4m as a C4IX
  program, with C4KE for it to boot;
- c4ix.vfs.txt: src/c4bb/fs/c4ix.vfs.txt with BIN_ALL and TOOLS for what
  is here and without libc's tests, through vfs-games.py with no games;
  c4ix.sizes and the host directories' listings, as build-images.sh
  makes them;
- c4ix-root.tgz: /usr, the repository as git has it, with the 64-bit
  libc4ix.c4l and libarc.c4l in /usr/lib and C4IX's headers in
  /usr/include. Not /build: b4ke inside builds everything the first time.

98 files, 19.1 MB. Left out: the games, libc's test programs, c4th, c4sp,
C4DOS and the ladder.

C4IX rebuilds this inside itself, as test-libjs's test-rebuild.sh has the
32-bit one do: `b4ke -j 4 -C /usr` on c4pc-host64w with 4 CPUs on threads
(`wait 7` first, for the root archive), 51,201,440,211 cycles in 266 s, no
step failed, and a second run finds everything up to date. Of what c4lc
builds (through c4sc), all 40 images are byte for byte the disk's up to
the end of S (libjs/tests/c4r-body.py; the disk's carry source maps):
the kernel, every program, the desktop, the shared libraries. The kernel
has 64-bit file positions as make's has them: C4IX's b4ke presets
`$(WORD)`, the machine's word in bytes, src/c4ix/BUILD.B4K compiles the
kernel `-D C4IX_WORD$(WORD)`, and c4ix.h turns C4IX_LFS on for
C4IX_WORD8 (the 32-bit kernel is unchanged). c4cc's four images have the
disk's sizes, and the rebuilt c4cc compiles a program that runs.
(Scratch: helios ~/c4pc64s/rb64.sh.)

## The ISO

Three entries after the 32-bit desktop's (src/c4pc/pc/grub.cfg): "C4IX
64-bit desktop (128 MB)", the same on every processor, and "C4IX 64-bit,
text (64 MB)", each `multiboot /boot/c4pcw64.elf` with `/boot/c4ix64.c4r`
and `/boot/disk64.tar drive`, each with the MMU (`--mmu`), as the 32-bit
entries have it.

For install (branch c4pc, 31025a4 on: it reads the ISO's
/boot/grub/disk64.cfg where the word is 64 bits), the ISO carries
src/c4pc/pc/grub-disk64.cfg: the same three entries booting
`-- --root @ROOT@` with no drive module, as grub-disk.cfg's do. Not booted
yet: `--root` comes with that branch.

## Stage two

- **The games**, one at a time: each its 64-bit build (lc64), its data
  on the 64-bit disk, its block in c4ix.vfs.txt, and its accelerators
  with WB-sized words where they read the game's (accel.h's kit is
  word-clean; its held writes and scratch are not yet).

  on branch c4pc), and the 64-bit root archive's /build, so b4ke inside
  starts with everything made.
